Explicit operator responsibility for other security/provider policies; no plugin-name detection masquerading as universal compatibility.

External mode: required valid same-site registration destination and optional same-site login destination, native login fallback; use page chooser if consistent with existing admin UI but support legitimate same-site account paths/query actions. Only effective while built-in registration is enabled, operational and the saved policy is valid; in SE-031.2 it must remain dormant (show pending explanation). No silent change to WP's global `users_can_register`. Other modes, deactivation, and invalid/unfinished setup restore normal native behavior. Explain invalidation/reopening and that disabling native registration does NOT disable every other account creation route.

Investigate actual current/floor native login-controller hooks including `login_form_register`, native registration URL rendering and action resolution. Prefer native narrowly scoped hooks, not a global registration/login URL takeover, rewriting all login requests, global flag mutation or broad authentication restrictions. Show an accessible explanatory response with sign-in/recovery and return to originating Sprint if safely available; no arbitrary return, no fabricated destination when there is no Sprint context. Investigate handling of native Register link so users are not sent to a dead end; if no supported narrowly scoped way to hide it, explain the limitation and provide safe blocked-route guidance rather than fragile global hacks. Do not disable native login, reset, logout, admin account creation, native network policy, WooCommerce checkout/My Account registration or independent external registration forms. Document any external system that actually uses native registration endpoint is affected by closing that endpoint, hence administrator choice. Test GET/POST variants, invalid requests and unaffected routes on current/floor WP, and real Woo/native account flows where applicable; if testing interception before SE-031.3 use isolated test-only operational readiness (never a production bypass/placeholder API exposed to guests). If safe implementation cannot be separated, defer active interception to SE-031.3 and record exact remaining work; do not expose enabled-looking protection that is not active.

When unchecked, show explicit persistent inline warning: native registration remains accessible and is not protected by Sprint Engine's form-specific abuse controls. Regardless of checkbox state, guidance on protection of other exposed registration paths, HTTPS, login abuse, caching and mail/security policies. No mandatory extra plugin or specific vendor promotion, no site-wide security engine. Operator must establish protection of all remaining public endpoints before enabling built-in signup. Native race limitations remain. Record accepted owner decision and replace spike's optional names recommendation: **first name and last name required** in SE-031.3, stored in standard WP profile fields; validate respectfully, international names/Unicode; collection is not marketing consent. Email and chosen password required, generated hidden username, native existing-account email sign-in/reset, admin-only initial native notification, no email verification/delayed checkpoints in initial scope.
