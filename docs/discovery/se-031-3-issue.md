## 2. Native account creation and authentication

Implement a small focused renderer/controller/account service in existing Runner route/decision boundary, not a global login handler, registration REST endpoint, user table, new rewrite or second authentication system. Resolve canonical saved Sprint and Availability on GET/POST; recheck mode/policy/role/readiness/classification/identity on POST and before creation where relevant; only eligible guest may create. Strict method/body/field allowlist and size limits. No private data, no attempt/progress write, no authenticated session switching, never trust request user/Step/Sprint/redirect selectors. Re-evaluate real access on fresh canonical return request. Native account creation with fixed fields via wp_insert_user, applicable user_registration_email/register_post/registration_errors and insertion hooks per spike, revalidate filtered values and uniqueness, preserve denied/approval policies; no global temporary filter workaround. Distinguish rendering/request-specific provider requirements that native hooks cannot satisfy. Respect native password hashing and slashing/whitespace semantics, test Unicode/password byte bounds on floor/current, never truncate or silently alter credentials. Subscriber explicitly and verify safe actual resulting identity; don't grant elevated roles or modify an existing account. Use a single appropriate native admin-only wp_send_new_user_notifications lifecycle; no duplicate setup/welcome email, no custom mailer, no verification link/code/delayed logout or checkpoints. Unverified email remains unverified; document residual squatting/recovery risks and no marketing consent. No commerce/email matching or historical order linking.

Use wp_signon and normal authentication filters/cookies only; supply server-derived canonical return hint compatibly with native MFA flow, correct query-value encoding per SE-031.2. WP_Error, challenge/redirect/exit, suppressed cookies or interruption must not be treated as successful authentication or circumvented. Never direct-set auth cookie/current user or retry using less restrictive API. Success means expected authenticated identity on fresh request and actual member access. For a persisted account whose auth/mail fails, keep account, offer sign-in/recovery/original link; no duplicate creation/mail or delete/overwrite rollback. Test native reset and existing email sign-in; don't promise automatic email/cross-device return or arbitrary external provider compatibility. Preserve URL filters and native policies.

## 3. Security implementation and bounded state

Use SE-031.1 experimental evidence as reference, not transplant MU fixture. Implement browser-bound cryptographically random guest state and signed action/Sprint/expiry token, one-use/replay reservation, Secure HttpOnly __Host- cookie (Path=/, no Domain, SameSite appropriate; explain cookie clearing/rotation and multi-tab behavior). Verify actual HTTPS and cookie injection resistance; guarded disposable test harness may use loopback HTTP only where expressly isolated, never a shipping bypass. Reject cross-origin/referrer/fetch metadata when supplied and incompatible; missing/null provenance not trusted, mandatory token; no WP guest nonce alone. Test no-JS, sibling-subdomain cookie injection, cross-Sprint/action/replay, expired/stale state, identity changes, refresh/multi-tab, login-CSRF and direct POST. No credentials, identifiers or tokens in URLs/logs/client storage; private/no-store/noindex including errors, cached guest/member separation, no external tracking/CAPTCHA dependency.

Implement proven bounded atomic abuse/replay storage using smallest viable design from spike (one non-autoloaded fixed-capacity row + per-site DB named mutex, or demonstrably equivalent proven atomic bounded design). Justify actual production caps, windows, budgets and privacy/expiry; diagnostic tiny values aren't launch defaults. Fresh authoritative reads; reserve atomically and recheck canonical email/username under owned lock; fail closed on lock/storage errors, bounded wait/work, exception-safe release, no silent transient fallback, release before notification/auth. Test DB reconnect/lock ownership, contention, saturation, expiry/replay, independent PHP workers, duplicate email and token, uncoordinated native/other creation residual; do not claim global uniqueness or change WP tables. Avoid holding transaction across external callbacks; document trusted hook limits. Bound stored HMAC-derived identifiers, no raw IP/email/password; use actual peer address, no blind forwarded headers, shared-IP and proxy handling/guidance. Include bounded periodic purge and on-request expiry, lifecycle cleanup of temporary state/scheduled event, no member data deletion. Test quiet-site/cron limits honestly. Accessible honeypot/timing optional signals, not mandatory puzzle or wait; no mandatory vendor CAPTCHA. Provide safe retry/help without an unprotected bypass; if appropriate narrowly scoped deny-only integration seam, no speculative SDK. Test current MariaDB and actual MySQL where available, connection failures/reconnect, fixed storage and reasonable load. If operational atomicity or security prerequisite cannot be proven, keep built-in disabled for that stack and report blocker rather than weakening protection. Account for platform rate controls; don't claim DDoS or all native auth protection.
