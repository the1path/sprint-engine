## Objective and decision boundary

Investigate a better first-use participant journey for standalone Sprint Engine Core. A guest following a published open Sprint link currently reaches native WordPress login, where registration may be unavailable or easy to miss; even when enabled the participant may not return naturally to the intended Sprint. Core already requires authenticated WordPress identity for progress, Dashboard and attempts; retain that architecture. This is a launch/onboarding improvement, not authorization to implement features. No evidence establishes why people uninstall or whether they prefer anonymous participation; do not infer adoption causes or add guest Sprints.

Owner's preferred direction for investigation: branded native participant registration and sign-in within the existing Runner/access screen, using WordPress account/authentication APIs, three explicitly selected registration modes, immediate access after successful policy-compliant registration for an open Sprint, layered spam protection, no mandatory email verification initially. Compare this against lower-risk native login/registration handoffs; challenge the preferred approach if security, compatibility or maintenance costs warrant it. Deliver recommendation and implementation plan for owner approval, not production code.

## A. Participant experience and registration settings

Assess three modes:
1. **Sprint Engine registration (recommended candidate)**: branded form for first/last name, email and password; native WP account creation; no purchase/order/cart; immediate login only if normal site authentication policies allow; return to exact canonical eligible Sprint and normal Ready to Start screen (no implicit progress/start). Existing users can sign in or use native password recovery. Consider whether a branded login form can safely participate in WP login security/MFA/SSO, or should delegate sign-in to native/external UI where needed.
2. **Use an existing registration system**: configurable valid same-site registration destination and optional login destination, native login fallback; send a validated return hint and document integration contract. External provider owns its form and post-auth redirect; no claim of universal support, no separate WooCommerce registration mode or matrix of plugin-specific redirects in initial scope. Consider a safe useful fallback if redirect is ignored.
3. **Invitation only**: sign-in for existing accounts, no public registration via Sprint Engine. Not a global restriction on other site's registration paths.

Propose safe unset state for fresh/existing installs (sign-in continues; no public signup until explicit privileged admin selection), persistent actionable setup notice on Sprint Engine admin screens and WP Dashboard for authorized admins; dismiss only after valid choice; reappear for invalid destinations/settings. Assess explicit site-wide WP users_can_register policy: do not silently bypass disabled registration or enable/change site-wide flags/roles. Explain whether independent opt-in can safely coexist with WP policy, what checks/guidance are necessary, and how multisite/network restrictions change the answer. No automatic public registration or elevated role. No setup requirement that prevents existing accounts or tutorial from working.

Propose branded screen, clear actions for open/free versus restricted/unknown access, responsive/accessibility, localizations, terms/privacy links as appropriate without implied marketing consent. Native WP password reset and mail notification responsibilities; no password storage/handling beyond native APIs, no mandatory verification initially (email remains unverified, explain risk and recovery). Do not require or expose any paid Pro feature in Core. Preserve publication/password/tutorial/availability and access denial rules; guest display must not expose private content or create an attempt. Restricted Sprints should have existing appropriate information/access/sign-in action, never imply account equals entitlement. Determine safe behavior if provider cannot classify guest access; fail closed.

## B. Security discovery (explicit go/no-go)

- Threat-model public account creation, login and handoff: account enumeration, automated account creation/email abuse, brute force/credential stuffing, CSRF including logged-out WP nonce limitations/login CSRF, replay/double submit/parallel registration, race-safe unique username/email and normalization, session fixation/identity changes, safe password handling/length, role/capability injection, redirect manipulation, cache leaks, multisite/network rules, signup restrictions, MFA/SSO/security/anti-spam hooks. Investigate WP's actual guarantees versus what we must own. Do not bypass authentication/registration policy filters or set auth cookies directly to circumvent MFA; distinguish account creation from sign-in.
- Recommend layered low-friction abuse controls without mandatory external CAPTCHA service: server validation, honeypot, bounded rate limits/timing with accessible fallback. Assess storage bounds/expiry/cleanup, atomicity/concurrency, shared IPs and reverse proxies (no blind forwarded-IP trust), privacy and availability/denial-of-service tradeoffs. Simple puzzle alone is not sufficient. Do not introduce speculative implementations. Define what can be guaranteed on ordinary shared hosting and what remains operator responsibility. Explain safe optional integration seam for site anti-spam/security providers; if secure immediate registration is not feasible, recommend alternative.
- Evaluate unverified email implications (misaddressed mail, account squatting, password reset, later customer account/purchase association); no silent email-based linking, no entitlement grants, no claim of verified identity. Compare native email setup/verification if recommended; optional code verification deferred unless security analysis demonstrates mandatory requirement and owner approves revised scope.
- Return URL derived from canonical server-resolved Sprint, validated same-site path/identity, no arbitrary redirect or trusting guest-supplied IDs, re-evaluate availability and entitlement after auth. Assess native WordPress email/password-reset return, external form limitations, cookies/session and private/no-store for dynamic forms/nonces, caching before PHP, cookie consent compatibility. No client-side sensitive persistence or exposure in logs/URLs. Provide failure handling for partial signup/login failure and accessible recovery; preserve existing user progress/records.
