## Decision and objective

Follow-up to SE-031 (#24) and merged discovery PR #25. Read the full report at `docs/discovery/se-031-participant-registration.md`, its issue snapshot, AGENTS.md, baseline specification and current development/validation records. Owner approves a controlled technical spike before committing to production implementation. Preferred outcome: an eligible guest opens a Sprint, creates an account with a simple branded form, is safely authenticated and reaches that exact Sprint's Ready to Start screen. Minimize friction and reuse as much native WordPress functionality as possible. Do not build a parallel identity/authentication system. If the evidence does not support safe, maintainable immediate sign-in, recommend a narrower alternative and stop.

## Agreed design constraints

- Standard single-site WordPress first. Core standalone, no WooCommerce dependency. Three future registration modes: Sprint Engine registration, existing registration system (administrator-owned form/login and redirect, native fallback), invitation only. Safe unset state; explicit administrator selection, actionable persistent setup notice, no automatic changes to WordPress global registration or role settings. Built-in public signup requires effective WordPress registration permission and safe least-privilege participant role. Network/multisite unsupported embedded flow must fail closed with native/network or existing-provider guidance.
- Focus on **new participant registration**, not a replacement login system. Candidate email, password, first/last name (assess optional names and email-as-login UX); existing-account sign-in and forgotten password delegated to native WP or configured provider. Use WordPress users, native password hashing, normal authentication/session cookies and recovery; no direct auth-cookie fallback, password persistence, duplicate account store, global login URL/redirect changes or unrelated website account management.
- Immediate access preferred; no mandatory email verification, delayed verification/checkpoint/logout, email codes, mandatory third-party CAPTCHA, guest progress, marketing automation, additional commercial functionality. Evaluate risks of unverified mailbox ownership, including account squatting/pre-hijacking, password recovery and commerce linking; recommend no-go or explicitly revised scope if safe initial release requires verification. Do not label email verified or infer entitlement, link historic orders/accounts by email or bypass provider verification.
- No attempt creation until explicit Start; canonical readiness, tutorial, publication, member access, progress and existing attempt/history invariants remain. A guest access presentation classification (open/restricted/unknown) is separate from access authority. Unknown or restricted must not promise free access. Existing Pro gate and denial hooks, current Core public APIs and existing installations remain compatible.

## 1. Compare established implementations

Review version-pinned open-source registration implementations of LifterLMS (especially open registration and external forms), WooCommerce and Tutor LMS where source is available. Trace form submission, role and registration policies, native WP APIs/hooks, authentication/redirect, notification, anti-spam, nonce/CSRF, concurrency, and security-plugin integration. Compare supported current/floor WordPress source (recheck discovery versions). Record source links/version and exact behaviors; distinguish copied patterns from proposed safeguards, source evidence from executed tests. Do not treat another plugin's behavior as security proof or copy code/dependencies wholesale.

## 2. Disposable prototype — actual evidence required

In guarded local disposable WordPress sites only, implement a minimal experimental flow, using synthetic users, isolated database, outgoing mail blocked and local captured mail. Do not commit prototype runtime code to Core or Pro. Record reproducible setup, commands, test cases, and outcomes; sanitized pseudocode/fixtures or a clearly isolated non-shipping harness only if needed to reproduce and explicitly marked as experimental. No production access, real credentials/users/orders/email, dependency installation on live sites, deployment or release.

Demonstrate account creation via native APIs, chosen password with no plaintext persistence, safe generated unique login with email sign-in, Subscriber role with capability checks, applicable native pre-registration validation/policy hooks and one appropriate native notification lifecycle. No raw request array passed to user insertion. Investigate native hook compatibility honestly: rendering/request-specific CAPTCHA/approval/MFA/SSO policies may require native/external UI; don't bypass policies or claim universal detection. Establish how a configured embedded mode can be safely supported, when it must refuse or delegate, and an actionable fallback. Verify that normal authentication produces expected authenticated identity on a new request, not merely WP_User or a cookie-setting call. Preserve canonical server-resolved Sprint return after authentication; safe fresh-request validation; already-authenticated existing users never switched or recreated; partial account creation/auth/mail failures recover through normal sign-in/reset. Native login/recovery fallback must return to intended Sprint where supported; document email/device/external redirect limitations.

## 3. Security and practical hosting

Turn SE-031's threat model into experiments. Prove (not just sketch) browser-bound guest CSRF and login-CSRF protections, replay/double-submit behavior, input bounds, native registration policies, safe role, normalization/duplicate handling, cross-origin/redirect attacks, no sensitive data exposure in URLs/logs/client storage, stale session/identity changes, private/no-store and cache isolation. Use server-side validation and low-friction layered abuse controls: accessible honeypot/timing where justified, bounded atomic rate/replay state, short expiry/cleanup, capacity/failure behavior, shared IP/proxy handling (no untrusted forwarded headers), independent worker concurrency and lock/replay tests, native/other registration race limitations. No standard logged-out nonce alone or transient read-modify-write counter represented as sufficient; no puzzle as sole defense. Investigate ordinary shared-host MySQL/MariaDB support, bounded resource cost and lifecycle; prefer smallest proven mechanism, no speculative framework. Document residual risks and operator responsibilities including native registration endpoint abuse, TLS, mail delivery, caching and real security-plugin coverage. Test native authentication rejection, actual selected MFA/security plugins where available (record exact versions), suppression/interruption, and SSO/approval flow where feasible; don't assume absence of known plugin implies safe policy. Explicit go/no-go for immediate sign-in and conditions on supported stacks. No unsafe direct wp_set_auth_cookie or other bypass.

## 4. Pro compatibility is a release gate

Read-only inspect current Pro integration (private source and customer specifics stay out of public report). Confirm no changes to existing access providers, entitlement OR rules, Workspace responses, history, Workbooks, Notes, Journeys, Collections, resources, Directory caching or existing member identity. Test candidate with existing unmodified Pro where feasible, both load orders, old Core with Pro and candidate new Core with existing Pro, open/restricted/hidden/unknown/tutorial and authenticated deny paths; fail safely when classification seam not present or not supplied. Identify minimal additive Pro presentation classification adapter as separately approved implementation if needed; no change to Pro source or commerce in this spike. Test standard WooCommerce same-account later checkout using synthetic disposable accounts and test orders only where safe (no live payments or outbound mail), including classic/block checkout as feasible, no automatic entitlement or historic order linking, existing customer identity/roles/records preserved. Explicitly distinguish real premium commerce/HPOS tests from doubles and mark unavailable tests NOT RUN. Do not require synchronized Core/Pro release to preserve existing functionality: if incompatibility found, identify blocker and migration/release ordering before release.
