## Exact extension contracts

All three actions are built-in template presentation hooks. They run on every
eligible render, rather than once per lifecycle transition. Their return values
are ignored. No callback means no new visible markup or behavior. Existing
creator completion CTA, restart, Dashboard links, card structure, grouping and
sorting stay intact. Template overrides are responsible for placing their hooks.

```php
do_action( 'sprint_engine/runner_completed_actions', $completed );
```

Runs after creator completion message/CTA, before Restart Sprint, only for an
authenticated, authorized completed Runner. The single array argument contains
exactly integer `sprint_id`, `attempt_id`, `attempt_number`. Core resolves the
Sprint from its route and takes attempt identity from ProgressService's canonical
completed state for `get_current_user_id()`. Request IDs and attempt selectors
cannot select this context. No history lookup or extra progress operation occurs.

```php
do_action( 'sprint_engine/dashboard_completed_card_actions', $item );
```

Runs once per eligible completed card, after its existing actions within
`se-dashboard__card-content`. The single argument is the existing safe Dashboard
item after the trusted `dashboard_items` filter and existing grouping/sorting:
`sprint_id`, `title`, `excerpt`, `runner_url`, `featured_image`, `duration`, `state`,
`completed_steps`, `total_steps`, `percentage`, `started_at`, `last_activity_at`,
`completed_at`, `attempt_id`, `attempt_number`. Types and nullable fields retain
the existing [development guide](../development.md) contract. No separate user ID
or other member records are supplied. The current WordPress identity is available
to trusted callbacks. In-progress, available and excluded cards never run it.

```php
do_action( 'sprint_engine/runner_access_denied_actions', $sprint_id );
apply_filters( 'sprint_engine/runner_show_public_access_gate', false, $sprint_id );
```

Both receive only the integer, Core-resolved ready Sprint ID (the filter also
receives its strictly false initial value). Availability independently checks
Sprint post type/publication/password, Launchable status, valid linear structure
and Step publication readiness first. No filter or denial action runs
for malformed/missing, unpublished, password-protected or unready content.

Authenticated access still passes through AccessManager. A denial creates the
existing `state: error`, `status: 403`, generic message plus an explicit internal
`access_denied_sprint_id` marker. The template requires that marker AND error/403
before firing the action. It never recognizes denial by message text. Ordinary
404/503 errors have no marker and cannot run the action.

The public filter runs only when anonymous and ready. No callback, false, null,
integers, strings, arrays or objects preserve the existing 302 WordPress login
redirect. Only exact boolean `true` selects the same generic denial screen,
adding `login_url` for a normal Login link back to the canonical Runner URL and
invoking the denial action. Core does not assess anonymous purchase entitlements.
No new route or rewrite is introduced.

Both denial screens retain generic heading/message, 403, DONOTCACHEPAGE,
`Cache-Control: private, no-store, no-cache, must-revalidate, max-age=0`,
`X-Robots-Tag: noindex, nofollow` and matching robots metadata. They do not render
title, overview, Step bodies, progress, arbitrary post metadata or mutation
JavaScript/REST nonce configuration. Upstream caches must bypass Runner/Dashboard
and respect these headers; PHP cannot control a cache that serves before WordPress.

## Trusted callback examples and boundaries

Example escaped presentation using already-authorized completion context:

```php
add_action( 'sprint_engine/runner_completed_actions', static function ( $completed ) {
    printf(
        '<p data-attempt="%s">%s</p>',
        esc_attr( $completed['attempt_id'] ),
        esc_html__( 'Your progress is saved.', 'my-extension' )
    );
} );

add_action( 'sprint_engine/dashboard_completed_card_actions', static function ( $item ) {
    printf(
        '<p><a href="%s">%s</a></p>',
        esc_url( $item['runner_url'] ),
        esc_html( $item['title'] )
    );
} );
```

Illustrative opt-in with an extension-owned policy, not Core metadata or APIs:

```php
add_filter( 'sprint_engine/runner_show_public_access_gate', static function ( $show, $sprint_id ) {
    // Extension must independently require publicly listed, genuinely restricted
    // content and an author-configured, validated information URL.
    return true === my_extension_can_advertise( $sprint_id );
}, 10, 2 );

add_action( 'sprint_engine/runner_access_denied_actions', static function ( $sprint_id ) {
    // Apply the same independent advertisement policy for logged-in denials.
    if ( ! my_extension_can_advertise( $sprint_id ) ) {
        return;
    }
    $url = my_extension_information_url( $sprint_id );
    printf( '<p><a href="%s">%s</a></p>', esc_url( $url ), esc_html__( 'More information', 'my-extension' ) );
} );
```

`my_extension_*` functions are illustrative consumer functions, not shipped APIs.
Callbacks are trusted installed server-side PHP; this is not a browser markup or
entitlement API. Callbacks must escape output, independently authorize destinations,
preserve generic denial/privacy and avoid storage mutations. Core cannot sandbox
trusted PHP that deliberately writes, changes headers or reveals data. The new
hooks themselves never grant access, call lifecycle services, expose another member,
or replace Availability/AccessManager. Existing REST authentication, nonce and
cross-Sprint checks remain authoritative.

`WP_SQLite_DB::ensure_database_directory()` directory `is_writable()` guard,
before opening the database or executing any Runner assertions. Inspection
reported the original OneDrive directory as ReadOnly/Directory/ReparsePoint,
with CodexSandboxUsers granted read/execute, while the normal temporary root

its existing SQLite file writable, and the normal temporary directory writable.

of the ReadOnly attribute was not retrospectively established. No ACL or ownership
change was needed or attempted.

The final test-only `mu-plugins` creation line cannot have caused this bootstrap
failure: it is reached after `wp-load.php`, concerns a different directory, and
was never reached in the failed run. The SQLite guard and Sprint Engine runtime
code were left intact.
