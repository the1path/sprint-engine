## A. Release-hardening summary

The local linear journey passes. Release acceptance remains conditional on the
target checks below; this is not a claim that all hosting/media checks passed.

Concrete findings and fixes:

1. All five plugin runtime assets used the unchanged plugin version `0.1.0`.
   Git deployments could change CSS/JS without changing its URL. Centralized
   content fingerprints now invalidate changed files, including ZIP deployments
   preserving file size/timestamp. Missing/unreadable files fall back safely.
2. Successful REST responses explicitly opted out of caching, while errors
   depended on core defaults. A namespace-scoped `rest_post_dispatch` hook now
   marks success, validation, permission and core authentication errors private
   and no-store. Other REST namespaces are unaffected by this hook.
3. Transaction failures previously returned a generic member error with no
   operational diagnostic. They now emit one generic PHP log message, without
   user IDs, content, nonce, SQL or exception details. Existing recovery logging
   remains. This is not an event store or analytics feature.
4. Native Runner action buttons explicitly use `appearance: none`. Browser
   computed-style checks confirm the existing primary/secondary design. No
   redesign, speculative specificity escalation or `!important` was needed.

No demonstrated cross-user leak, unsafe write, progress-loss, incorrect
advancement, rollback, fresh-activation or package defect remains in local tests.

## D. Security and failure review

Reviewed Runner, routes, template, both member REST writes, AccessManager,
editor REST, metadata/metabox/AJAX/Quick Edit boundaries and persistence code.

- Authentication: real cookie requests reject missing nonce (401) and invalid
  nonce (403). Direct dispatch also requires a current user and REST nonce.
  Anonymous Runner redirects preserve the canonical same-site login return.
- Authorization: AccessManager governs member admission; its grant/deny filter
  cannot bypass the adapters' separate authentication. Admin authoring requires
  manage_options and per-post edit capabilities; nonce alone is insufficient.
  Native Quick Edit retains WordPress nonce/capability/slug uniqueness handling.
- Tampering: zero, negative, decimal, alphabetic, huge overflow, encoded slash,
  backslash/NUL, exponent and plus-prefixed REST IDs are rejected. URL-captured
  IDs select resources; body/query user/Step/Sprint fields cannot change the
  current identity. Complete derives and validates the persisted parent.
- Isolation: alternating real cookie requests to the same URL preserve A's
  completion and B's Start state. Browser A advances/completes while B starts
  independently and remains at Step 1. Their writable-page nonces differ.
- Privacy: errors use allowlisted messages; no private titles/content, database
  details or paths are forwarded. Injected service failure renders recovery and
  exit without a write control. Native editor reads are administrator-only.
  The private CPTs have no public Step rewrite. Escaping is contextual; authorized
  blocks use normal WordPress content filters and temporarily scoped post globals.
- Templates: existing realpath/readability/PHP/installed-code-root restrictions
  and fallback tests pass. No request-controlled template path is introduced.
- Routes: both trailing-slash forms, unknown/Step/malformed slugs, encoded
  separators/NUL and query-only invocation were checked. Feed/post/preview
  selectors cannot replace the Runner's canonical query. Ordinary pages retain
  their rendering/assets. Existing admin tests cover slug changes/new URL;
  no old-slug redirect is added.
- Failure UX: safe 404/403/503 contexts, real invalid-nonce responses and a held
  then failed browser write were exercised. Content stays visible on failed
  completion, status announces uncertainty and retry, and success requires a
  confirmed server response. Node tests include network and malformed JSON.

No new public endpoint, access integration or trust boundary was added.

## E. Caching and assets

The target host showed new SE-006 markup with default-looking controls despite explicit
button CSS in the repository. The reproducible code defect was unchanged asset
URLs across deployments. Latest CSS produces the intended green primary and pale
secondary controls locally; no local external override was demonstrated.
Therefore stale asset caching is the likely cause, not a proven target host cache
trace. Browser/server/CDN response bodies on the target host still need inspection.

`Assets::version()` combines plugin version with SHA-256 of bytes. All five
Runner/admin CSS/JS assets use it. Equal-size edits with preserved timestamps
change the version; timestamp-only changes do not. Missing files/directories
fall back to plugin version. Read failures are suppressed/caught without paths
in member output. The helper reads only paths supplied by trusted plugin code.
It does not disable caching, add random values, version core assets, persist a
shared cache or require a build manifest. An unreadable file cannot be reliably
fingerprinted and must have its deployment permissions corrected.

Runner retains DONOTCACHEPAGE, private/no-store/no-cache headers and noindex.
REST success/errors now share explicit no-store semantics, verified over HTTP
including core nonce failure. Asset URLs contain hashes, not filesystem paths.
Completed/error/unrelated pages omit member write config; admin scripts remain
Sprint-editor-scoped. An upstream cache serving before WordPress must bypass
`/sprint/*` and honor REST no-store (or bypass `/wp-json/sprint-engine/v1/*`).
This ticket does not configure target host/CDN infrastructure.

## F. Data integrity, backend and lifecycle

All original progress/structure regressions passed. These exercise duplicate and
simultaneous Start/Complete, stale browser retries, future-Step rejection,
completed Start retries, immutable completion/start timestamps, missing current
progress rows, corrupt status/pointers, foreign/deleted/trashed/detached Steps,
all-complete repairs, invalid start/next links and unsupported storage engines.
Fault injection verifies rollback at creation, completion, advancement, final
completion and commit boundaries; failed operations do not publish events.
Historical rows are retained. Corrupt links are not guessed or rewritten by
member requests; authors must repair the current linear order.

Transaction support checks and per-Sprint locking are unchanged. Two independent
PHP workers actually ran against SQLite. No disposable MySQL/MariaDB/Docker
backend was available in the local tools checked: **TARGET-ENVIRONMENT CHECK**
for InnoDB, isolation, rollback, concurrent writes and persistent object caches.
Never run these destructive suites against the development site's authored database.

Fresh/repeated activation, version/schema options, normal init, failure/recovery,
downgrade refusal, rewrite lifecycle, deactivation/reactivation and uninstall
retention are covered. Existing network activation still rejects safely; no
multisite provisioning or migration change. No per-request rewrite flush.

Public action argument shapes remain:

- `sprint_engine/sprint_started(user_id, sprint_id)`
- `sprint_engine/step_started(user_id, sprint_id, step_id)`
- `sprint_engine/step_completed(user_id, sprint_id, step_id)`
- `sprint_engine/sprint_completed(user_id, sprint_id)`

Actions run after successful commit, once per transition; retries do not replay
them. A process crash/throwing third-party listener can interrupt delivery;
durable delivery remains out of scope. Filters retain
`user_can_access_sprint(allowed, user_id, sprint_id)` and
`runner_template(default_path, authorized_context)` under `sprint_engine/`.

## H. Known limitations and deferred decisions

Welcome Step may feel redundant. This remains a product decision after technical
hardening. Neither state was merged, removed or restructured.

No restart/reset, content versioning, branching, dashboard, commerce, automation,
custom player or playback tracking. Avoid live restructuring with active users.

full Gutenberg authoring and real media remain unverified on target. Distribution
licensing and public packaging/release remain SE-008 concerns.

## I. Target host post-merge checklist

1. Deploy only the plugin directory. In a private browser/hard refresh, confirm
   updated `ver=0.1.0-<hash>` asset URLs and successful CSS/JS responses. Confirm
   Start, Continue, Complete and Save & Exit visibly use the intended styling.
2. Author/publish a five-Step Gutenberg Sprint, reorder/reload, enable Launchable,
   verify Runner URL/Copy URL and Quick Edit slug. Verify old/new URLs as intended.
3. Use controlled test members: Start, complete, refresh, leave, resume, finish.
   Alternate two users at the same URL and confirm independent state/nonces.
4. Verify actual native audio, YouTube/video, PDF/file viewing and download.
5. Check desktop/mobile, zoom/reflow, keyboard skip/focus/action controls and
   interrupted/expired-nonce feedback. Confirm current content remains on failure.
6. Confirm host/CDN bypasses Runner and respects REST no-store. Ordinary pages
   should have no Runner assets/configuration.
7. Deactivate/reactivate with a backup and controlled test data; verify content
   and progress retention. Check installed PHP/WP versions and InnoDB tables.
8. Run destructive concurrency/rollback/minimum-version suites only on a separate
   disposable target-like installation, never the authored target host database.
