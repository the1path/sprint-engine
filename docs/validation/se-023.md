## Editor and request design

WordPress 6.0 and 7.1 gate Gutenberg's built-in frontend preview on the post
type's REST `viewable` flag. The Step and Sprint types are non-viewable, and
`get_preview_post_link()` only constructs a native preview URL and appends its
preview arguments for viewable post types. A URL filter alone cannot provide the
built-in control. Preview Step uses Gutenberg's View menu extension point when
available and the Options menu extension point in older or narrow editors.
[WordPress preview URL source](https://developer.wordpress.org/reference/functions/get_preview_post_link/)
and [Options menu extension point](https://developer.wordpress.org/block-editor/reference-guides/slotfills/plugin-more-menu-item/).

An edited title or block document is submitted to the Step's existing WordPress
autosave REST endpoint with the editor's standard authentication. The request
contains title and content and may change an automatic draft to an ordinary
draft. Step metabox fields and the featured image use their ordinary save flow.
An existing author draft can receive the autosave directly. For a revision,
the new tab includes the autosave ID returned by WordPress. A clean editor opens
saved content directly. An autosave failure closes the loading tab and displays
an editor notice. [WordPress autosave REST API](https://developer.wordpress.org/rest-api/reference/post-revisions/#create-an-autosave).

The site-root preview checks the administrator's logged-in session, Step-specific
nonce, `manage_options`, `edit_post` for the Step, and the Step's type and status.
For a revision it verifies that the requested ID matches the current user's
WordPress autosave for that exact Step, including the parent and author IDs.
Accepted and rejected requests send private/no-store, noindex/nofollow and
no-referrer headers. The cache bypass marker is `sprint_engine_step_preview`.
[WordPress per-author autosave lookup](https://developer.wordpress.org/reference/functions/wp_get_post_autosave/).

The preview uses the built-in Runner template, Step article, branding CSS,
attachment helper and normal WordPress content filters. Position and total come
from the saved linear structure. The preview has its own template state, without
member access, progress, mutation JavaScript or member template hooks. WordPress
can replace an author's autosave on subsequent edits, so the preview URL follows
that autosave and expires with its session nonce.

## Checks

- The Step preview browser suite passed on WordPress 7.1.2 with PHP 8.3.35 and
  SQLite integration 1.8.0, both with Core alone and with Pro 0.1.0 active. It
  also passed on WordPress 6.0 with PHP 8.0.30 and MariaDB 10.11.11, including
  the legacy Options menu. Both sites used non-default database prefixes.
- Chrome/Playwright exercised the actual Gutenberg menu and a separate preview
  tab for a saved draft under an unpublished Sprint, an edited draft, a published
  Task Step with a published parent, and a draft without a parent. Checks cover
  branding, Stage, position, estimate, Task guidance, lists, native image and
  audio playback, featured image and a fixture embed at 1440, 768 and 390 px.
- HTTP checks rejected anonymous requests, subscribers, an administrator without
  the Step edit capability, missing or mismatched nonces, copied links, and
  another administrator's autosave ID submitted with a valid nonce. The tests
  checked private/no-store/noindex headers on success and denial. Native public
  post and REST selectors withheld Step content. Each administrator could view
  their own autosave while the published post retained its saved content.
- The fixture guarded member access, template and lifecycle hooks and failed on
  any participant-table query during preview. Exact before/after comparisons
  passed for Core attempt and Step progress rows and an existing Pro Workspace
  response. The Workspace block showed its unavailable message in preview. The
  published Sprint opened on its canonical member Runner URL.
- All 19 existing Composer test scripts passed individually with fresh
  disposable fixtures as required, totalling 1,777 passing assertions. This
  includes authoring, Structure Manager, Runner and Dashboard HTTP, authenticated
  REST, access, progress, restart and attempt history.
- Existing Runner browser journey passed at 1440, 900 and 390 px. Start,
  complete, exit/resume, restart and activation retention preserved the expected
  attempt and completion rows across two users.
- PHPCS, PHP lint, JavaScript syntax, 39 JavaScript tests, release metadata and
  the exact 47-file runtime package check passed.

## Changed files

- `src/Plugin.php` and `src/Runner/StepPreview.php` register the editor control and
  authorize the frontend request.
- `assets/js/step-preview.js` opens the tab and requests a native autosave when
  the Step's title or content has changed.
- `src/Runner/Runner.php`, `src/Runner/Presentation.php`, `templates/runner.php`
  and `assets/css/runner.css` share the built-in Runner presentation.
- `tests/browser/step-preview-fixture.php` and `tests/browser/step-preview.cjs`
  exercise the editor, preview route, member data and optional Pro Workspace.
- `docs/development.md` and this record document the workflow and evidence.

## Rendering limits

Save the featured image, Stage, mode, estimate and structure changes before
previewing them. Native content blocks use the same theme and block rendering
hooks as the built-in Runner. Embedded media remains subject to its provider's
normal availability and permissions. The browser fixture uses a deterministic
oEmbed response and a local audio file. Third-party blocks that require a live
participant context may show their fallback state, as Pro Workspace does.
