## Runtime and transaction contract

- `restart_sprint( $user, $sprint, $expected_attempt_id )` accepts an in-progress
  or completed canonical attempt. Under the existing Sprint-row transaction lock,
  it compares the supplied rendered identity with the latest owned attempt before
  any progress write. A superseded/mismatched identity returns
  `sprint_engine_progress_stale_attempt`; it never allocates another attempt.
- An in-progress source changes **only** `status` to `restarted`. Original IDs,
  number, pointer, UTC timestamps (including `updated_at` and null `completed_at`)
  and every Step progress record remain unchanged. No Sprint-completed event or
  fabricated completion time is emitted. A completed source is wholly untouched.
- Source status update, server allocation of N+1 and first-Step insertion are one
  transaction. The replacement begins `in_progress` at the current first Step,
  with zero completions, own UTC timestamps and null completion time. Any failed
  update/insert/commit rolls the entire operation back and emits no events.
- Existing Sprint-started and first-Step-started actions retain their argument
  shapes, including trailing attempt ID/number, and fire once after commit.
- Concurrent restarts share the existing lock and attempt-aware unique keys. One
  succeeds; the other returns a stale conflict. A competing completion either
  commits to its original attempt before restart or conflicts after restart.
  Same-Step identity across attempts cannot bypass the check.
- `get_attempt_history()` includes `restarted` records as stored, with existing
  ordering/ownership and read-only semantics. A restarted run is neither active
  nor completed. State/resume/start resolve only latest; an inconsistent latest
  restarted row fails safely instead of falling back to historical progress.
- No database deletion, Pro response query/write, migration or schema change.
  Existing `varchar(20)` status accommodates `restarted`.

## REST and member presentation

**Intentional transport/API change:** Restart and Step Complete require
`expected_attempt_id` from the displayed attempt. The corresponding PHP service
methods also require it semantically; omitted/default-null identity fails closed.
Missing/malformed IDs return HTTP 400; valid stale IDs return HTTP 409 with no
writes/events. Start is unchanged. Custom PHP/REST clients and template overrides
must carry the rendered identity; resolving latest at write time is unsafe.
There is no runtime legacy fallback.

Runner JS sends its localized captured attempt; Dashboard JS sends the completed
card's captured attempt. All owned service test/fixture callers were updated.
The disposable-only test identity helper simulates rendering for existing fixture
setup; stale/concurrency tests explicitly capture and reuse a source identity.

REST retains current-user/nonce, URL resource identity, Step membership/order,
AccessManager, Availability, safe errors and private/no-store headers. A small
optional second ProgressService constructor argument supplies a trusted mutation
guard. Core REST repeats authentication/nonce, current member, AccessManager and
Availability **after** the transaction lock and cache invalidation, before writes.
Direct trusted PHP callers retain their responsibility for member policy; guards
must not start nested progress transactions. No entitlement logic moved into a
repository and no Pro dependency was added.

The authenticated, authorized in-progress Runner has Restart beside Save & Exit,
with distinct DOM IDs and a native modal dialog. It explains Step 1, preserved
History, read-only superseded work and loss of unsaved responses. Cancel receives
initial focus; Cancel/Escape perform no request or progress change. Confirm uses
the existing endpoint and canonical URL. Restart/completion share one pending
guard, disable both controls, and recover together after a failed request.
Completed Runner native confirmation and all completion hooks/actions are retained.
Browsers need native dialog support for the new in-progress action.

## Remaining compatibility work and limitations

**The combined Core/Pro feature is not ready for deployment.** Pro was not modified
or tested. Its follow-up ticket must recognise/display restarted history; retain
owned Workbooks as accessible, read-only records; never offer Continue/edit;
bind Workspace saves to the rendered attempt and reject stale/foreign/historical
writes before mutation under a lock that serializes with Core's Sprint-row lock;
preserve completed History/Workbook behaviour and all saved responses; and test
same-Step tabs, save/restart contention, multiple restarts, auth and retention
against updated Core. A latest-at-save lookup or pre-lock check is insufficient.
Core remains independently installable; the guard seam requires no Pro dependency.

Not executed: MySQL/MariaDB transaction/contention checks (no configured disposable
backend), PHP 8.0/WordPress 6.0 minimum matrix (runtimes unavailable), full Pro suite,
Plugin Check, other browser engines and staging/production acceptance. No History
UI, snapshots or Step/content change detection was added. New dialog action needs
native browser dialog support. Existing generic request errors require reload to
resolve a stale identity or lost successful response; retrying cannot create a
second replacement for the same source.
