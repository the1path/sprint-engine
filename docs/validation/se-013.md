## Routing, authentication and private responses — PASS

`Dashboard\Routes` owns `^sprint-engine/dashboard/?$` and the public namespaced
query variable `sprint_engine_dashboard`. `Routes::url()` uses `home_url()` and
`user_trailingslashit()`. Matching requires both WordPress's matched rule and
the exact path, with strict end-of-string validation. Query-string flags, suffix
paths (including encoded newline), generic `/dashboard/` and `/sprints/` requests
cannot invoke the application. Runner's existing rule and slug handling are intact.

On matched requests the request filter replaces parsed variables with only the
Dashboard flag, `post__in => [0]` and `ignore_sticky_posts`. Preparation resets
the main query; unrelated posts, home and feed state do not reach document hooks.
Unrelated requests/templates retain their existing behaviour. Ordinary init only
registers. Activation registers both routes before its flush; deactivation removes
both before its flush, retaining progress. A successful 0.1.0 → 0.2.0 upgrade
also registers both routes and performs one soft flush, without a Permalinks save
or reactivation. Failed installation leaves old rewrites intact; subsequent ordinary
requests do not flush again. Follow-up evidence is recorded below.

Authentication occurs before enumerating Sprints. Anonymous visitors receive a
WordPress login redirect with the canonical Dashboard as `redirect_to`; no titles,
images, progress or access decisions are returned. Real loopback HTTP checks pass.
Every item is bound to `get_current_user_id()`, never request-supplied identity.

Matched responses define the conventional `DONOTCACHEPAGE` when absent, call
`nocache_headers()`, send `Cache-Control: private, no-store, no-cache,
must-revalidate, max-age=0` and `X-Robots-Tag: noindex, nofollow`, and include
`<meta name="robots" content="noindex, nofollow">`. Real authenticated HTTP with
feed/post spoofing returned 200 and those headers/metadata. Admin bar and normal
canonical/old-slug redirects are disabled only on the matched application route.
Upstream cache configuration was not changed or tested.

## Eligibility, access and read-only state — PASS

A card requires all of:

1. `sprint_engine_sprint` post type.
2. Published status.
3. No post password.
4. Empty current `Runner\Availability::reason()` (including Launchable and valid
   linear structure).
5. Current member accepted by `AccessManager::can_access()`.

The implementation calls these existing boundaries before preparing title,
excerpt, image or Runner URL. A real access filter denies an otherwise eligible
Sprint in integration and browser tests. Its title, authored excerpt, action URL,
card, distinct image alt text and image source URL are absent from integration
HTML. Browser HTTP excludes the denied card/title/action and unavailable Sprint.
Unpublished, password-protected, non-Launchable and foreign-linked content is
also excluded. No unauthorized item reaches the items filter.

Each eligible authorized Sprint calls **`ProgressService::get_state()` once**.
No `resume_sprint()`, start, complete or restart runs on Dashboard viewing. This
deliberately uses canonical service semantics rather than adding a batch read or
analytics engine. Existing service snapshot/locking queries remain unchanged.
Any canonical read error causes one generic 503 without partial cards, guessed
actions, database/service errors or internal details.

Exact enrolment and Step-progress snapshots before/after resolve and template
render compare equal, including every timestamp/attempt field. Browser snapshots
also remain equal after Dashboard viewing and following Start Sprint to the Runner
Start screen. A stale current-Step pointer stays untouched by Dashboard reads;
the Runner remains responsible for repair. Another member sees their own Available
states instead of the first member's active/completed attempts, despite supplied
`user_id`/`attempt_number` request values.

`not_started` → Available; `in_progress` → In Progress; `completed` → Completed.
Highest positive attempt number remains canonical inside ProgressService. Attempt
1 completed plus Attempt 2 active yields only one In Progress card. Available
items have null attempt identity. Historical attempts are neither exposed nor
displayed, and restart plus subsequent reads preserve every pre-existing progress
row exactly.

## Items, sorting and extension hooks — PASS

The normalized flat item contains:

| Field | Shape |
| --- | --- |
| sprint_id | integer |
| title, excerpt | authored plain strings; excerpt never generated from content |
| runner_url | canonical Runner URL |
| featured_image | WordPress attachment-helper HTML or empty string |
| duration | `Meta::sprint_duration()` array, empty when unconfigured |
| state | not_started / in_progress / completed |
| completed_steps, total_steps | canonical integer counts |
| percentage | canonical numeric percentage |
| started_at, last_activity_at, completed_at | nullable UTC database datetimes |
| attempt_id, attempt_number | nullable integers, internal context only |

`sprint_engine/dashboard_items($items, $user_id)` runs only after authentication,
Availability, AccessManager and successful canonical state resolution for every
included item. Trusted PHP extensions must preserve item shape and member access.
Core groups/sorts the filtered list and works without any extension. No speculative
Pro API is added.

Sections appear In Progress, Available, Completed, omitting empty sections. Active
items sort by activity descending; completed items by completion descending;
Available items by title A–Z. Timestamp ties use case-insensitive title then numeric
Sprint ID. Null/invalid UTC timestamps sort last without warnings. Integration
tests cover recent-versus-old dates, title ties and ID fallback, null ordering and malformed
dates/null bytes. Attempt ordering never uses those timestamps.

`sprint_engine/dashboard_template($path, $context)` uses the existing Runner path
safety algorithm: reject wrappers/null bytes, resolve real paths/symlinks, require
a readable local PHP file and containment inside plugin/mu-plugin/theme code
directories. Uploads and repository test files are rejected. Safe installed-plugin
PHP is accepted. Default context is state/status/sections, or a generic error.

## Presentation, navigation, restart and Settings — PASS

Standalone semantic header/main/section/article markup, skip link, headings,
labelled native progress, human-readable rounded percentages and card-local polite
status regions are implemented. No JavaScript tabs. Authored excerpts/titles escape
stored HTML. Valid featured images use WordPress helpers and sanitized markup;
absent excerpts/images/durations are omitted, with no fallback artwork. Completed
cards indicate 100% and never display attempt numbers.

Dashboard-specific CSS is scoped to `body.se-dashboard`. Its responsive grid fits
three desktop columns and one narrow-screen column, aligns cards to their natural
height, and keeps a lone card at a readable width. Shared `RunnerBranding::css()`
provides primary/foreground/background/surface/text/muted/corners and derived
colours; the existing logo helper/class is retained. Default desktop/mobile
screenshots were inspected. A separate branded browser run confirms saved colours,
primary text, card corners and logo at 390px without progress mutations.

Available's Start Sprint link opens the existing Runner overview without enrolling.
Continue Sprint opens the canonical Runner/current Step. Runner Save & Exit now
links to Dashboard without writing; Start/Completion return via Back to My Sprints.
Existing Runner assertions are preserved and augmented with canonical URL/read-only
checks. The completion author's message/CTA remains separate and unchanged.

Completed cards offer Restart Sprint and View Completed Sprint. Restart uses
the existing authenticated `POST /sprint-engine/v1/sprints/{id}/restart` endpoint;
no second backend exists. Delegated events require explicit translated confirmation.
Cancel causes no request, busy state, disabled control or mutation. Confirm disables
only that card's control, sends current REST nonce and same-origin credentials,
checks HTTP success, `success === true`, `state === in_progress`, and the exact
expected canonical Runner URL, then redirects. Foreign-origin destinations are
rejected. Failed/invalid responses restore the control with a safe local message.
No client user/attempt selector is sent.

At both 1440px and 390px the browser journey covers Dashboard → Start overview,
Continue → current second Step → Save & Exit → unchanged Dashboard progress,
View Completed → original completion message/CTA → Dashboard, cancel restart with
zero requests, rejected restart recovery, confirmed retry → first Step/zero progress
→ Save & Exit → In Progress reclassification. PHP post-journey checks verify
Attempt 2 and exact historical rows/lifecycle retention. Keyboard focus has a
visible 3px outline, actions have at least 44px height, progress has label relations,
optional images load, and no viewport overflow occurs.

Sprints → Settings includes a read-only Member Dashboard canonical URL and View
Dashboard action. Existing `manage_options` gate is retained and explicitly tested
against a subscriber. No setting, option, content, progress, dashboard widget or
notice is added for this link.

committed SE-013 implementation, `cc9f9e95930a22a98951184d5d4708f55dda7bea`.

plugin version does it explicitly register Sprint/Step post types, Runner and
Dashboard routes, then call `flush_rewrite_rules(false)`. WordPress owns deferral
until `wp_loaded` when called early in init. Failed installation does not flush;
matching current markers skip installation/flush, and schema-only recovery does
