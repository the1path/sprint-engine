## Decisions and resulting behavior

- The service still validates the entire nonempty linear structure, then traverses
  explicit stored start/next links. It never invents links or repairs authoring
  metadata. StructureManager remains the authoring authority.
- Inside the existing transaction/Sprint-row lock, subtract completed Step IDs
  for the exact user/Sprint/attempt from the current validated chain. The first
  remaining ID is the next requirement, even when the saved pointer remains a
  valid incomplete Step later in that chain.
- Resume updates a differing pointer to that requirement and retains normal UTC
  activity semantics. Existing `enter_step()` reuses visited started rows and
  inserts/emits start only for genuinely absent rows. No historical row is deleted
  or reset. Attempt IDs/numbers and all original start/completion times survive.
- Before a new completion, both the submitted Step and saved pointer must match
  the earliest incomplete requirement. Otherwise the existing out-of-order error
  maps to safe REST **409**, private/no-store, with reload guidance and zero writes
  or events. SE-019 expected-attempt validation still occurs under the same lock.
- After persisting completion once, subtract the updated completed set from the
  chain again. Advance to its earliest remainder, skipping already completed Steps
  in any position. No remainder uses the existing finish transition, including
  when the last outstanding Step is no longer the terminal Step in the chain.
- Valid already-completed Step retries return current state before any transition.
  They never repair a stale pointer, advance into inserted work, reset timestamps
  or repeat hooks. Removed/foreign Steps still fail membership checks first.
- Completed attempts remain completed, including after insertions. Restarted
  attempts remain historical. All-complete resume repair retains its existing
  completion timestamp/event semantics. Reads and Dashboard never repair progress.
- Progress counts intersect historical completed IDs with the current valid chain.
  Removed/moved Step rows remain stored but do not inflate current percentages.
- Runner's default ProgressService repeats current-member, AccessManager and
  Availability checks after the lock/cache invalidation, closing its preflight
  readiness race. REST already supplied this locked guard. Trusted PHP callers
  retain their existing internal draft-content contract and responsibility for
  member policy/guard configuration. No entitlement logic moved into repositories.
- Public ProgressService signatures, history payload, routes, nonce/authentication,
  expected_attempt_id and lifecycle hook shapes are unchanged. Events remain
  post-commit only; rollback publishes none. No Pro runtime dependency or Journey,
  snapshot, curriculum versioning, warning/notification or automatic restart.
