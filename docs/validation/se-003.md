> Historical validation record: results, release stages and remaining checks below

Validated on 23 September 2026. This ticket adds only the internal PHP progress

## Responsibilities and specification review

Reviewed against specification sections 1–5, 7, 9–10, 13–16 and the SE-003 ticket.
No specification conflict or schema correction was required. The SE-001 tables,
unique keys, schema/plugin versions and PHP 8.0 / WordPress 6.0 baseline remain
unchanged. SE-002/SE-002.1 runtime code and existing tests are unchanged.

- `Progress/EnrolmentRepository` provides `find(user, sprint)`, `create(row)` and
  `update(id, fields)` for canonical persistence. IDs in returned enrolments are
  integers, with nullable current Step retained. State, current Step, activity
  and completion updates share the focused update operation.
- `Progress/StepProgressRepository` provides `find(user, sprint, step)`,
  `create(user, sprint, step, utc_time)`, `complete(user, sprint, step, utc_time)`
  and `completed_ids(user, sprint)`. Conditional completion preserves an existing
  completion time and reports whether a row transitioned. Completed ID queries
  deliberately retain historical Steps; the service filters counts by the chain.
- Repositories perform database persistence only and throw a generic exception
  on failure. Trusted internal callers supply validated fields and transaction
  boundaries. Neither repository authorizes a member or decides a transition.
- `Progress/ProgressService` owns validation, transitions, progress projection,
  recovery and the specified events. It is instantiated through the existing
  plugin autoloader and requires no new bootstrap hooks or public routes.
- `Progress/Transaction` owns the database boundary and the existing Sprint row
  locking protocol. It adds no tables or migrations.

SQL values use WordPress prepared queries / insert / update APIs. Table names
come from `$wpdb->prefix`; queries avoid the newer `%i` placeholder to retain
WordPress 6.0 compatibility. Operational rows are read directly, without a second
object-cache representation that could diverge after rollback.

## Public service API

All five operations return an associative state array or a `WP_Error`:

| Method | Behaviour |
| --- | --- |
| `start_sprint(user_id, sprint_id)` | Starts a launchable, structurally valid Sprint once. Reuses an existing `not_started` row; returns existing in-progress/completed state without resetting it. |
| `get_state(user_id, sprint_id)` | Reads state without creating or repairing progress. An unenrolled user receives `not_started`. |
| `get_progress(user_id, sprint_id)` | Returns the same canonical state, including counts and percentage. |
| `complete_step(user_id, sprint_id, step_id)` | Completes the current valid Step, follows its explicit next link, or finishes at the valid terminal Step. Completed-Step retries return canonical state. |
| `resume_sprint(user_id, sprint_id)` | Preserves a normal current Step and updates activity; repairs stale pointers or all-complete enrolments where safe. Does not start an unstarted Sprint. |

State fields: `status`, `sprint_id`, `current_step_id`, `completed_steps`,
`total_steps`, `percentage`, `started_at`, `last_activity_at`, `completed_at`.
Unset pointers/timestamps are null. Percentage is a deterministic number rounded
to two decimal places, bounded by counting the intersection of completed IDs and
the valid chain. Completed enrolments report 100%, including when content later
changes. Historical completions outside the current chain do not inflate counts.

The constructor accepts an optional UTC clock callable for deterministic tests.
The production default is `current_time('mysql', true)`; site timezone settings
do not affect stored operational dates.

**Authorization boundary:** These are trusted internal PHP operations. They
validate user existence, IDs, Sprint/Step types, membership and structure, but do
not authorize the caller to act for the supplied user. Future member adapters
must authenticate, bind the user ID to the current member and authorize through
AccessManager before invoking the service. No temporary entitlement checks are
introduced here.

## State transitions and idempotency

- Start creates one enrolment (`in_progress`, calculated start Step, UTC
  start/activity/create/update times, null completion) and starts the first Step.
  The existing unique keys remain a final duplicate guard. Repeated starts never
  reset the original start or activity time and never restart a completed Sprint.
- Completion requires an existing in-progress enrolment and the current valid
  Step. Missing current-Step progress can be created and completed atomically.
  A different incomplete Step, foreign Step or removed Step is rejected.
- Completing a previously completed valid Step returns current state without
  writes, advancing, changing timestamps or repeating events. This applies after
  advancement and after final completion.
- Advancement reads `_se_next_step_id`; it does not derive the next Step from
  position. Final completion additionally requires all currently valid Steps to
  be complete, sets status/completion once, and clears `current_step_id`.
- Reads never update progress/activity or repair pointers. Explicit resume is
  the operation that updates meaningful return activity and repairs stale state.
- Resume preserves completed rows, including deleted/trashed/detached content.
  A stale or already-completed current pointer selects the first incomplete Step
  along the current valid chain. If all valid Steps are completed, it repairs the
  enrolment to completed, preserving an existing completion timestamp if present.
  Successful repairs write a generic anomaly message to the PHP error log,
  without personal data, SQL or paths.

## Structural assumptions and safe failure

All operations require a nonempty current structure accepted by
`StructureManager::is_linear()`. The service then traverses the persisted start
and next links, checking membership, supported modes and integer metadata. Order
remains the authoring input; explicit links remain the runtime representation.

Membership follows SE-002.1: draft, pending, private, scheduled and published
Steps are included; trashed and auto-draft Steps are excluded. The service does
not introduce a publication gate. New starts require Launchable. Disabling it
does not reset or block retries/resume for an existing enrolment with a valid
structure; future access/publication policy belongs to caller layers.

Trashing/deleting a linked Step can leave an invalid chain. The service does not
rewrite authoring metadata or guess links. An administrator must review the
remaining Steps and Save order before pointer recovery can succeed. Parent moves
through the existing StructureManager already repair the affected lists. An
empty, foreign-linked, self-linked or otherwise corrupt chain returns an error,
including on reads; no progress history is removed.

Live restructuring is still discouraged as specified in section 13. For example,
a valid current Step that now leads into an already-completed Step, or a terminal
Step with earlier incomplete Steps, fails safely. This ticket does not invent a
content-versioning policy or silently skip work to accommodate arbitrary reorder.
Malformed enrolment states return an error rather than being reset.

## Transactions, concurrency and event timing

Every operation owns a transaction and checks that WordPress content tables plus
both progress tables support rollback (InnoDB metadata on MySQL/MariaDB; the
official SQLite integration supplies compatible semantics). Unsupported engines
fail before progress writes. No storage-engine conversion is performed.

A no-op update locks the Sprint post row before reading the structure or progress.
This serializes first-start races, repeated completions and SE-002.1 manager
changes using its existing locking protocol. Locks are per Sprint, including
different users: a deliberate simple correctness choice for v0.1. Even read-only
state operations briefly acquire this lock for a coherent snapshot, but create
no enrolment/progress records and alter no content fields. Content caches are
invalidated before validation; progress repositories query the database directly.

Errors/exceptions roll back the enrolment and Step writes together and return a
generic `se_progress_persistence` error without exposing database details. IDs,
launchability, structure and order errors have distinct service error codes.
Recursive calls during an active progress transaction are rejected. Do not call
the service inside an external transaction: it owns START/COMMIT/ROLLBACK.

The four specification actions are queued during transitions and dispatched only
after a successful commit, with the exact specified arguments:

- `sprint_engine/sprint_started(user_id, sprint_id)`
- `sprint_engine/step_started(user_id, sprint_id, step_id)`
- `sprint_engine/step_completed(user_id, sprint_id, step_id)`
- `sprint_engine/sprint_completed(user_id, sprint_id)`

Failed operations and idempotent retries dispatch none. Initial and next-Step
entry emit `step_started` only when a new progress row is created. Repair of an
all-complete enrolment emits Sprint completion when no completion timestamp
already exists. Post-commit listeners may read through the service safely.

These are synchronous WordPress actions, not a durable delivery queue. Process
failure after commit can lose delivery, and a throwing third-party listener can
interrupt later listeners/events without undoing committed progress. Retries do
not redeliver committed events. Durable outbox/delivery and CRM listeners are
outside this ticket. Arbitrary direct SQL/metadata writes and native REST
restructuring outside the manager's locking protocol are not serialized by it.
