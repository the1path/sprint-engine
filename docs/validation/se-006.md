# SE-006 — Sprint Runner UX

> Historical validation record: results, release stages and remaining checks below
> refer to this ticket at the time it was recorded. Core 0.2.0 is now released.

## Implementation and scope

The standalone Runner now has a quiet utility navigation area, compact Sprint
header, readable Step card, progress bar and separated action area. Its neutral
green/grey palette, system fonts and scoped CSS add no brand or external dependency.
Ready to start remains a separate overview with estimated Sprint duration and an
explicit Start Sprint button. Viewing it still writes no progress. Completion
shows the Sprint title, a restrained done state, canonical 100% and a return link.

Changed files: `src/Runner/Runner.php`, `templates/runner.php`,
`assets/css/runner.css`, `tests/integration/runner.php`, and `README.md`.
Added this document and `tests/browser/fixture.php`, `tests/browser/runner.cjs`.
`assets/js/runner.js` is unchanged. No schema, ProgressService, persistence,
access/availability rule, REST contract, metadata definition or URL change.

## Context and presentation decisions

The authorized `step` context adds `mode`, `estimated_minutes`, `position`
(nullable) and `is_terminal` (boolean). Metadata uses the existing Meta reader;
mode is allowlisted to task/content. Task Steps show a small instruction cue;
positive duration renders as About N minute(s). Unset/zero duration is omitted.

Position uses the existing ordered valid Step list, checks membership, agreement
with the canonical total, and StructureManager::is_linear. Ambiguous position is
null and omitted. This is presentation only: current_step_id still selects the
Step and ProgressService still navigates via explicit next_step_id. A validated
last Step with no next link displays Complete Sprint; otherwise the label is
Complete & Continue. Both keep the same action ID and REST complete endpoint.

Completed count, total and percentage come directly from ProgressService.
Visible percentages round to whole numbers; the native progress value retains
canonical precision and has a visible accessible label. Position and completed
count remain distinct (Step 3 of 6 versus 2 of 6 complete).

Save & Exit is a normal home-URL link, with no new write. The action-area note
explains that completed Steps are saved and the current Step requires explicit
completion. The generic in-progress cue “Continue where you left off” is used
on every in-progress view. No browser-session heuristic or database state was
added. Optional completion dates were omitted.

## Blocks, responsive layout and accessibility

All CSS rules are scoped under `.se-runner`. Reusable utility/header/progress,
metadata/content/action/button/completion/error classes govern presentation.
The content width is constrained; mobile primary buttons fill the card width.
Controls have at least 48px height, visible focus, hover, disabled and aria-busy
styling. Status feedback remains adjacent to the action with a polite atomic
live region. Existing pending protection, same-origin nonce writes, uncertainty
messages, retry behavior and canonical reload are unchanged. No sticky controls.

Normal WordPress block/content rendering is preserved for paragraphs, headings,
lists, quotes, images, galleries, buttons, file links, tables, embeds, native
video/audio and PDF objects. Images/video scale proportionally, native audio
fills available width, YouTube ratio wrappers retain their aspect ratio, and
file objects stay inside the card with viewport-bounded height. Tables and pre
blocks allow inner scrolling. File/download controls use secondary styling;
Gutenberg buttons receive legible default colors while retaining explicit author
colors. No custom media player or PDF reader is introduced. Browser support and
site block/theme styles still require deployment verification.

The heading hierarchy, skip link, semantic progress and native controls remain.
The primary action stays after content and never covers media on mobile.

## Reproducing browser checks

Use the existing README disposable WordPress setup and loopback HTTP server.
Install/use Playwright and Chrome in the development environment only. With
SE_TEST_WP_ROOT and SE_TEST_DISPOSABLE=yes set:

```sh
php tests/browser/fixture.php > .tools/se006-fixture.json
node tests/browser/runner.cjs .tools/se006-fixture.json
php tests/browser/fixture.php .tools/se006-fixture.json
```

The last command removes only that fixture's posts, user and plugin progress.
The local JSON contains an expiring test login cookie: keep it in ignored .tools,
never commit it. NODE_PATH may locate an existing Playwright install;
SE_BROWSER_CHANNEL defaults to chrome and SE_BROWSER_OUTPUT defaults to
.tools/se006-browser. Screenshots/manifests are not packaged or committed.
The browser check only accepts a localhost/127.0.0.1 URL.

## Deferred product UX question

Ready to start → Start Sprint → Welcome Step can feel repetitive when an author
uses an introductory first Step. This is explicitly deferred to final v0.1
refinement/hardening. Future options include using Start as the introduction,
beginning the first actual Step immediately after Start, or author guidance
against separate Welcome Steps. None is selected or implemented in SE-006.

No specification clarification or architectural assumption was required. No
restart, dashboard, branching, media tracking or next-ticket work is included.
