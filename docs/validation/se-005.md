## HTTP contract

- `POST /wp-json/sprint-engine/v1/sprints/{id}/start`
- `POST /wp-json/sprint-engine/v1/steps/{id}/complete`

Both operations require WordPress's authenticated current user and an
`X-WP-Nonce` header generated with `wp_create_nonce('wp_rest')`. WordPress's
normal cookie authentication remains in place. Missing cookie nonces clear the
current user in core and yield 401; invalid nonces yield core's 403. The explicit
permission callback also rejects missing/invalid headers for internal REST
dispatches. This ticket deliberately requires a nonce for all callers; external
application-password/mobile authentication is not offered.

Only URL-captured positive decimal integer IDs select resources. Overflow,
zero, negatives and malformed IDs return 400. Body/query `id`, `user_id`,
`member_id` and `sprint_id` cannot override URL identity, current user or the
Step's stored parent. Complete reads `_se_sprint_id` and verifies membership.
Supplying a foreign Step operates only against its real parent and that parent's
access/enrolment; it cannot advance the Sprint named in an extra parameter.
An unstarted foreign Sprint fails through ProgressService.

Availability::reason is reused for published, non-password-protected,
Launchable, structurally valid Sprints. Protected/unavailable Steps cannot be
completed. Assigned draft Steps follow the existing authoring release model:
the published Launchable parent is the release gate. Availability does not
perform member authorization. AccessManager and its existing
`sprint_engine/user_can_access_sprint` filter run before any progress write.
Only `get_current_user_id()` is passed to ProgressService.

Start delegates to `start_sprint`; Complete delegates to `complete_step`.
There is no direct repository write, independent progress calculation or
position-based navigation in REST or JavaScript.

Success is HTTP 200 with private/no-store and the following allowlisted fields:

```json
{
  "success": true,
  "sprint_id": 123,
  "state": "in_progress",
  "runner_url": "https://example.com/sprint/example/",
  "progress": {"completed_steps": 1, "total_steps": 5, "percentage": 20},
  "current_step_id": 457,
  "completed_step_id": 456,
  "sprint_completed": false
}
```

The last two fields appear only on Complete responses. Final completion reports
`completed`, null current Step, 100%, and `sprint_completed: true`. Start on a
completed enrolment returns its existing completed state without restarting.
No arbitrary metadata, timestamps or private Step content are returned.

## Errors and retries

Errors use standard WordPress `{code, message, data: {status}}` envelopes.
Adapter errors have stable `se_write_{status}` codes and generic translated
messages. Internal messages, SQL, paths and private titles are never forwarded.

| Status | Conditions/service codes |
| --- | --- |
| 400 | Invalid route identifier |
| 401 | Anonymous identity; `se_progress_user` |
| 403 | Missing/invalid nonce in adapter; access denial; core nonce failure |
| 404 | Unavailable content; `se_progress_sprint`, `se_progress_step`, `se_progress_not_launchable`, `se_progress_structure` |
| 409 | `se_progress_state`, `se_progress_out_of_order` |
| 503 | `se_progress_persistence` and unknown service errors |

Repeated Start preserves original timestamps. Completed-Step retries return
current canonical state, without extra rows, counts, advancement or lifecycle
events. Future incomplete Steps fail. Correctness remains in the unchanged
transactional service, not in button disabling. A lost response may mean the
write committed; retrying or reloading safely resolves the uncertainty.

## Runner interaction and scoping

Authorized not_started/in_progress contexts receive a semantic type=button
Start Sprint/Complete & Continue control after overview/current Step content.
Completed/error pages contain neither control. Status feedback uses role=status,
polite aria-live and aria-atomic. A noscript message explains the requirement.
Viewing Ready to start still creates no enrolment.

Runner enqueues the dependency-free script and configuration only for a matched,
authenticated writable context, never unrelated pages, admin, errors or completed
states. Configuration contains only the current endpoint, wp_rest nonce,
canonical URL and busy/error text. Existing private/no-store, DONOTCACHEPAGE,
noindex, authentication and normal Gutenberg/audio rendering remain intact.

The script ignores duplicate clicks while pending, disables the button, sets
aria-busy and announces Starting Sprint/Saving progress. It sends a same-origin
POST with X-WP-Nonce. Success requires HTTP success, JSON success=true, a valid
resulting state and a returned URL equal to the server-configured canonical URL.
It navigates to that canonical URL, with no Step parameter. It never increments
progress or swaps Step content optimistically. Failed/unconfirmed responses
leave content visible, show retry/reload guidance and re-enable the button.

## Remaining deployment checks and limitations

On the development WordPress site, deploy only this plugin and verify:

1. Existing Runner URL and logged-out login return still work.
2. An unstarted test member sees Start; click opens Step 1; refresh retains it.
3. Complete advances one Step; double-click does not skip; finish reaches 100%.
4. Leave mid-way and return to the stored Step; URL remains `/sprint/{slug}/`
   throughout and no normal Step permalink appears.
5. Native Gutenberg content and real audio playback work with the site's plugins.
6. Interrupt/fail a request and confirm useful uncertainty/retry feedback.
7. Unrelated pages have no Runner script; host/server/page cache excludes Runner.
8. Validate target MySQL/MariaDB locking/transactions and concurrent writes on a
   separate disposable installation, never the site's authored data.

JavaScript is required for writes. Nonce expiry requires page reload. Live
restructuring/versioning and restart are outside scope. SQLite concurrency tests
and sequential duplicate HTTP submissions do not establish production MySQL
concurrency behavior. No specification change or new architectural assumption
was needed.
