## API and architecture

Exact signature:

```php
public function get_attempt_history( $user, $sprint = null )
```

`ProgressService` validates identifiers and projects canonical enrolment records.
It does not use `operate()`, `Transaction`, chain validation, availability checks,
the lifecycle clock, resume/completion repair, restart, or StepProgressRepository.
Existing lifecycle methods are untouched. Service construction still creates its
existing repositories but history never invokes the Step repository.

**MEMBER-FACING CALLERS MUST APPLY THEIR OWN AUTHORIZATION POLICY.** This trusted
PHP API does not invoke AccessManager or commercial access checks. Consumers must
bind the user to the authenticated member and authorize their presentation and
destinations independently. It intentionally allows a trusted internal caller
to select an existing user; it is not an authenticated member REST endpoint.

Each public record contains exactly:

| Field | Contract |
| --- | --- |
| `attempt_id` | Integer enrolment identity |
| `sprint_id` | Integer persisted Sprint identity |
| `attempt_number` | Positive integer sequence |
| `status` | Stored status, unchanged |
| `current_step_id` | Integer/null stored pointer, including stale pointers |
| `started_at` | Stored UTC datetime string/null |
| `last_activity_at` | Stored UTC datetime string/null |
| `completed_at` | Stored UTC datetime string/null |
| `created_at` | Stored UTC datetime string |
| `updated_at` | Stored UTC datetime string |

No user ID, raw repository ID, SQL, table names, content, per-Step reconstruction
or completion counts appear in the public projection. History is metadata rather
than a content snapshot. An existing user with no attempts receives `array()`.

User validation reuses ProgressService's strict positive integer/decimal-string
ID check and `get_userdata()` existence check. Boolean, float, array, object,
overflow, injection-like, zero, negative and nonexistent IDs fail safely with
`sprint_engine_progress_user`. A supplied Sprint uses the same ID validation and
must have current post type `sprint_engine_sprint`, otherwise it returns
`sprint_engine_progress_sprint`. Draft/private/trashed/unlaunchable Sprints can
still be identified. Deleted posts cannot be identified for a supplied filter.
The global call makes no current-Sprint lookup and retains deleted/trashed IDs.

Ordering is defined as `sprint_id ASC, attempt_number DESC, attempt_id DESC`.
Within a supplied Sprint this is newest sequence first with descending attempt
identity as a deterministic tie-breaker. Timestamps do not determine recency.

`EnrolmentRepository::list_attempts( $user, $sprint = null )` executes one focused
SELECT of only the needed columns from `$wpdb->prefix . 'sprint_engine_enrolments'`.
It prepares `user_id = %d`, requires `attempt_number > 0`, optionally adds a
prepared `sprint_id = %d`, and appends a static ORDER BY. There are no post joins,
per-Sprint/per-attempt loops of queries or Step progress queries. Numeric fields
are normalized in the repository as in `find()`; the service renames `id` to
`attempt_id` in an explicit projection. The existing indexes/schema are unchanged.

History does not create or repair enrolments and never issues INSERT/UPDATE/DELETE,
transaction/locking commands or schema changes. Existing schema/installation
guards fail safely rather than attempting installation. Database failures return
a generic `sprint_engine_progress_persistence` WP_Error, suppress database output,
and restore the previous suppression setting in `finally`.

History survives Step reorder/content/block changes, unlaunchability, broken
chains and stale current pointers without altering historical rows or timestamps.
Global reads preserve a missing Sprint's persisted ID for consumer fallback.

## Dashboard hook

`sprint_engine/dashboard_header_actions` fires once in `templates/dashboard.php`,
immediately after the introductory paragraph inside the header and before Sprint
sections. Its only argument is the already-authorized `$sprint_engine_context`:
ready `state/status/sections`, or safe error `state/status/message`. Real anonymous
requests redirect before rendering. Unrelated requests select their normal
template and do not fire this action. No listener changes no display behaviour.
Callbacks escape their own output and authorize their destinations; Core does not
sanitize arbitrary trusted callback HTML. The intentional slash hook has the
project's narrow PHPCS naming exception and explanatory comment.

## Security and performance review

Strict IDs prevent coercion and malformed input; prepared SQL binds the exact
requested user and optional Sprint at SQL level. The table identifier uses only
WordPress's trusted runtime prefix, never submitted data or a hard-coded prefix.
The explicit projection excludes arbitrary user/internal data, and safe error
paths expose no SQL, table names, traces or developer paths. Selecting another
user is a trusted PHP capability requiring consumer authorization; no new public
transport exposes it. Deleted-content durability requires no current content
reads in the global case. Each history call has exactly one enrolment query;
WordPress may independently read its existing user/post/options caches on a cold
call. No persistent caching or new stored personal data is introduced.
